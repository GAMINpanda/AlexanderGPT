# AlexanderGPT research notes

AlexanderGPT aims to resolve useful coding tasks with a small local model and one inference slot. The current reference configuration is Qwen3-4B Q4_K_M with 4K or 8K working context on a Windows RX 570 with 4 GB VRAM. The practical question is which work the harness can do deterministically so the model spends its limited context and generation budget on understanding the task and proposing a change. Reliable operation on CPU-only hardware, including a Raspberry Pi 5, is a longer-term research target.

## Design rationale

### Store the conversation and select the working context

The terminal agent stores original questions and answers in workspace-scoped SQLite sessions. It includes recent turns and retrieves relevant older excerpts using FTS5. The standalone harness also stores task state and sources. When the prompt fills, the context builder drops lower-priority material from the working prompt and leaves the stored conversation available for later retrieval. It counts tokens on the actual rendered llama.cpp template and reserves output space before admitting optional evidence. This lets a fresh source excerpt answer the current question while a follow-up can still recover an older filename or decision. Keyword recall can miss paraphrases, and keeping a record does not guarantee the model will use it correctly. [Context assembly](server/harness_context.py) · [Memory implementation](server/chat_memory.py)

Liu et al. found that models in their experiments could perform worse when relevant information appeared in the middle of a long prompt. That motivates testing evidence selection and placement at a fixed budget. The paper does not establish the effect size or best placement for Qwen3-4B. Swival offers a related engineering example by bounding tool output before it enters the conversation and preserving task state across compaction. [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/) · [Swival context management](https://github.com/Swival/swival/blob/master/docs.md/context-management.md)

### Find code before asking the model to interpret it

The terminal agent searches Git-visible Python declarations before ranking a bounded set of ordinary references. Exact compound identifiers and words in nearby docstrings help rank definitions. It parses the selected files to qualify the declarations it shows, and gives Qwen numbered excerpts. The search runs without inference. Aider's Tree-sitter map and Agentless's progression from files to symbols to edit ranges motivate this staged design. A persistent index remains an experiment for larger or multilingual workspaces. [Terminal search](server/terminal_agent.py) · [Aider repository map](https://aider.chat/docs/repomap.html) · [Agentless](https://arxiv.org/abs/2407.01489)

RepoCoder uses iterative retrieval and generation for code completion. It suggests a possible follow-up for vague queries whose first retrieval misses the target. An extra generation call has a measurable cost at 4K on this hardware, so the current navigation path uses deterministic retrieval. [RepoCoder](https://aclanthology.org/2023.emnlp-main.151/)

### Use executable feedback for proposed edits

The model proposes an explicit replacement range from a numbered excerpt. The harness validates the range, checks Python syntax, previews the diff, and checks the original bytes on approval. This follows SWE-agent's use of numbered file views and line-range edits. An invalid proposal gets at most one retry with the specific validation failure. For requests to add Python tests, the harness checks that existing test functions keep their ASTs and that a new test function exists. Executing the configured tests still checks behaviour. The current loop handles one existing file at a time. [SWE-agent interface](https://swe-agent.com/0.7/background/aci/) · [SWE-bench paper](https://proceedings.iclr.cc/paper_files/paper/2024/hash/edac78c3e300629acfe6cbe9ca88fb84-Abstract-Conference.html)

## Evidence so far

- The frozen 4K chat benchmark passed 6/6 for both variants. Total generation calls fell from 12 to 6 and median end-to-end latency from 42.87 s to 10.91 s. That experiment changed several defaults together, including reasoning mode, and used one run per case. It cannot isolate the effect of context selection or predict real repository task success. [Benchmark method and results](docs/HARNESS.md#tests-and-benchmark)
- A disposable Git fixture demonstrated a one-call edit proposal followed by browser approval and a passing test. A separate cold 4K run found a login handler with 47 ms of search and answered a follow-up from history without rescanning. These checks establish that the workflows work on small examples. [Agent verification](docs/HARNESS.md#terminal-agent)
- A subsequent 4K terminal trial used the parcel fixture and a 1,728-file CPython standard-library snapshot. Among seven scored tasks it passed session recall, partially met three navigation or overview rubrics, and failed two lookups and a billing edit. The billing proposal failed exact-match validation before any write. CPython navigation search took roughly 2.1–2.4 s in this run, and retrieval preflight missed two target definitions. A supplemental test-writing trial on a reference-fixed copy passed the test command while replacing an existing test. These are single-attempt results. They motivate measuring definition recall and citation accuracy separately and checking test-suite preservation alongside exit codes. Full transcripts are stored in the local ignored task directory.
- Staged Windows 4K reruns after the changes recovered all three CPython targets. Search took 0.59–0.74 s across the successful navigation turns. Identifying the HTML base method required distinguishing its definition from a subclass override. Numbered edits fixed the billing bug. The test-preservation check rejected a proposal that removed existing tests, and a separate run added a fifth passing test. Another added test failed because it called the wrong API. These runs support the workflow changes and leave repeatability and edit reliability open for measurement.
- A matched 4K comparison held Qwen, seed, reply limit and sampling fixed. With the same excerpts, both the agent and a short direct prompt solved two source lookups. Without excerpts, Qwen failed the exact-location rubric on both. Hand-selected excerpts reduced input tokens substantially. For billing, both prompts produced the same passing patch under the same response schema and validator. The agent needed two calls after proposing an inverted range, while the short prompt needed one. These single runs separate the benefit of source retrieval from the cost of the surrounding prompt. The local ignored task directory records all four conditions.
- A follow-up at seeds 7, 19 and 42 compared the ordinary lookup with a single-definition prompt at 4K. Both passed all three attempts, while input fell from 1,100 to 218 tokens and median elapsed time fell from 19.25 s to 5.20 s. A different short edit prompt failed all three seeds because its generated Python did not pass syntax validation. The fuller edit prompt passed all three after retry and remains the default. These results cover one exact lookup and one billing edit. They justify a narrow fast path and broader comparisons before shortening other prompts.

The initial four-case edit benchmark verified 6/12 runs, with regional pricing and additive test writing each at 0/3 eventual success. Adding specific syntax feedback and AST-anchored test insertion raised eventual success to 9/12, with regional pricing recovering 3/3 on retry. Inspection showed the edit path discarded retrieved implementation excerpts when a request named the test file. After preserving those excerpts, the full three-seed run passed 12/12 edits: 9 passed on the first proposal, and all 3 regional pricing cases passed after retry. The additive test passed on its first proposal for all three seeds. Focused lookups passed 3/3 at 141 input and 13 generated tokens per turn, with about 2.6 seconds elapsed. This is promising evidence on four synthetic tasks, not a reliability estimate for larger projects. The raw report is `.local-ai/edit-benchmark/results.json`.

## Research priorities

| Order | Experiment | Decision criterion |
| --- | --- | --- |
| 1 | Test on a larger pinned repository. Include navigation, history follow-up, bug repair, additive test writing, and a two-file task. | Record expected definitions and executable checks. Separate retrieval failure, invalid edit, failed verification, and budget exhaustion. Compare first-proposal and eventual verified success, calls, tokens, and time. |
| 2 | Compare current text search, an inexpensive filename and symbol index, and a token-budgeted map. Start with Python AST for supported fixtures. Try Tree-sitter when the workload warrants broader language coverage. | Measure whether the right definition reaches the top three and the rendered prompt. Measure cold build time, warm lookup time, update cost, and index size. Add dependency ranking if the ablation shows that it helps. |
| 3 | Compare recent-only history, recent plus FTS recall, and compact task state at the same context size. Include exact identifiers, paraphrased decisions, and conflicting facts superseded by a newer turn. | Score recall accuracy, handling of updated facts, useful evidence admitted, and prompt tokens. Test 4K and 8K separately and compare evidence placement within each budget. |
| 4 | Compare the terminal edit-and-test loop with Aider on the same model. Add multi-file edits or richer repair only where failures show a need. Profile CPU-only execution after establishing the desktop baseline. | Compare verified task completion first, then calls, tokens, time, and peak RAM or VRAM. Keep failed or partial edits visible in the results. |

For comparisons, pin the repository revision, GGUF, quantisation, runner build, sampling profile, context size, and hardware. Reset the worktree and relevant history between runs. Record cold and warm runs separately and report cache settings, repeated runs, and the number of tasks attempted. Time search, prompt processing, generation, and tests independently where instrumentation permits. Track input, generated and cached tokens, retries, and peak memory. Score navigation against ground-truth definitions and changes against executable checks. Keep chat smoke results separate from agent completion results.
